How the math works

The roofline ceiling is the tensor-core peak for the selected precision (spec mode) or the same peak derated by an efficiency factor (realistic mode):

P_eff = e_comp · P_spec          e_comp default 0.70 (Advanced slider)
b_eff = e_bw · b_spec           e_bw default 0.75 (Advanced slider)
A = min(P_eff, b_eff · I)
FLOPs(prefill) = B·S·2·N_active + 2·B·S²·L·(H + H_kv)
FLOPs(decode/token) = 2·N_active + 2·L·S·(H + H_kv)
DRAM bytes(prefill) = W + B·S·(2·L·H_kv·b_kv + 16·H)
DRAM bytes(decode/step) = W_stream(B) + B·(2·L·S·H_kv·b_kv + 2·L·H_kv·b_kv + 16·H)
Arithmetic intensity I = FLOPs / DRAM bytes
Achieved = min(P_eff, b_eff × I)
Ridge point = P_eff / b_eff

Where N_active is active parameters (MoE models use only their per-token active experts), W is total weight bytes, H hidden size, H_kv KV-head dimension (GQA/MLA shrink the KV cache), L layers, S sequence length, B batch size. The 16·H per-token term is a rough activation-traffic estimate. Memory capacity includes weights, KV cache, and a FlashAttention-style activation buffer estimate of 16·B·S·H bytes. Multi-GPU results assume ideal tensor-parallel scaling with weights and KV sharded across GPUs.

MoE decode weight streaming. A dense decode step rereads all weights once per step, W_stream(B) = W. An expert-parallel MoE only rereads the union of experts the batch routes to. With E experts and top-k routing, a batch of B tokens touches an expected E·(1 − (1 − k/E)^B) experts, so W_stream(B) = W_shared + W_exp·(1 − (1 − k/E)^B), where the shared (always-active) weight share is estimated from total and active parameter counts. At B=1 this streams roughly the per-token active expert set; a large batch saturates back toward W. Total weight bytes are still used for prefill and capacity checks.

The realistic efficiency defaults (compute 70%, DRAM 75%) are calibrated against the measured benchmark records on the Validation page — see docs/simulation-methodology.md for the equations, sources, and error definitions. Even spec-mode analysis remains an upper bound that ignores kernel-launch, communication, and scheduling overheads.

The simulation itself runs in a C++ core (cpp/sim.cpp, exposed through a C ABI), wrapped by Python (simulator/core.py via ctypes) and served to this page by a local API server (simulator/server.py). The JavaScript here only renders.

For the step beyond a single GPU — how data, tensor, pipeline, and expert parallelism move bytes between chips and when communication becomes the bottleneck — see the companion interactive visualization How to Parallelize a Transformer for Training.
